# 知识库维护说明

本文说明“协议明镜”本地知识库的用途、文件格式、更新流程和常见问题。知识库由项目维护者手工整理，模型只能读取已经导入的本地材料，不会因为填写了 `source_url` 就自动联网抓取或更新内容。

## 1. 知识库是什么

知识库位于仓库根目录的 `knowledge/`，每个 Markdown 文件代表一份背景材料。当前材料主要用于：

- 提供用户协议审阅的检查点和常见风险背景；
- 帮助专业 Agent 理解费用、隐私、内容授权、账号和争议解决等问题；
- 让模型在分析时通过 `search_knowledge` 或只读 `knowledge_shell` 查询相关材料；
- 在分析结果中记录引用过的知识条目 ID。

知识库不是当前网站协议的替代品。协议中的事实必须引用本次扫描得到的协议原文；知识库只能补充审阅框架、法律背景或案例线索，不能用来“补写”协议没有提供的事实。

## 2. 文件位置和导入结果

源文件：

```text
knowledge/*.md
```

导入后生成：

```text
data/knowledge.db
```

`knowledge.db` 是 SQLite 只读检索库，包含普通元数据表和用于全文检索的 FTS5 索引。运行导入命令时，程序会删除并重新生成整个数据库，而不是增量合并。因此，`knowledge/` 才是需要提交和维护的权威内容，`data/knowledge.db` 是可以随时重建的生成物。

如果使用自定义路径，可通过 `.env` 设置：

```dotenv
KNOWLEDGE_DB_PATH=/path/to/knowledge.db
```

## 3. 新增或修改材料

在 `knowledge/` 下新增一个 `.md` 文件。文件名主要用于默认 ID，建议使用稳定、易读的短横线命名，例如：

```text
knowledge/cn-personal-information-retention.md
```

文件需要包含 YAML frontmatter。推荐格式如下：

```markdown
---
id: cn-personal-information-retention
title: 个人信息保存期限审阅要点
source: 某法规或公开材料的整理
jurisdiction: CN
document_type: regulation
effective_date: 2025-01-01
source_url: https://example.com/source
---

## 适用范围

说明材料适用于哪些网站、服务、地区或分析场景。

## 核心内容

用简洁、可检索的段落记录规则、定义、例外和适用条件。

## 使用边界

说明不能由这份材料直接推出哪些结论，以及需要回到协议原文核验的事项。
```

### 字段说明

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| `id` | 否，推荐填写 | 知识条目的稳定唯一标识。未填写时使用文件名去掉 `.md` 的结果；不要让不同文件产生相同 ID。 |
| `title` | 否 | 展示名称。未填写时使用文件名。 |
| `source` | 否 | 材料来源说明。未填写时为 `local`。 |
| `jurisdiction` | 否 | 适用法域，例如 `CN`、`US`、`EU`。 |
| `document_type` | 否 | 材料类型，例如 `regulation`、`case`、`guideline`、`checklist`。 |
| `effective_date` | 否 | 材料生效日期，建议使用 `YYYY-MM-DD`。 |
| `source_url` | 否 | 原始来源地址，仅用于记录来源，不会触发自动抓取。 |

frontmatter 之外的正文会被写入全文索引。标题、正文和 `source` 都可被检索；其他元数据会保存在文档记录中，但当前检索接口主要返回 `id`、`title`、摘要和匹配分数。

## 4. 内容编写规范

### 4.1 优先写可复用的判断框架

适合放入知识库的内容包括：

- 需要检查哪些条款；
- 常见风险的触发条件；
- 不同法域或服务类型下的区别；
- 术语定义、例外和常见误读；
- 案例事实、处理结果和可迁移的审阅经验。

不要只写“某网站有风险”这样的结论，应说明风险为什么成立、适用边界是什么。

### 4.2 区分事实、规则和推论

建议使用明确的小标题，例如：

```markdown
## 已知规则
## 常见风险
## 例外情况
## 审阅问题
## 不应直接推出的结论
```

不要把未经核实的传闻、模型生成内容或单一案例的结论写成普遍规则。法规、案例和平台政策应记录版本或日期，避免新旧材料混用。

### 4.3 保留来源和适用范围

每份材料至少应在 frontmatter 的 `source` 中写清来源，并在正文中说明：

- 材料覆盖的国家或地区；
- 适用的服务或用户类型；
- 材料的版本、生效日期或整理日期；
- 是否为原文摘录、摘要、案例整理还是审阅清单。

较长的材料应按主题分节，避免把多个法域、多个版本和多个服务混在一个没有边界的文档里。

### 4.4 不替代协议原文

知识库中的法律背景不能证明某个网站协议一定违法、无效或必然导致诉讼结果。模型仍需：

1. 在当前协议快照中找到对应原文；
2. 用原文作为告警证据；
3. 把知识库仅作为背景或审阅方向；
4. 对缺失的附件、定义、补充规则标记为不确定，而不是猜测。

## 5. 更新和验证流程

修改或新增材料后，在仓库根目录执行：

```bash
pnpm knowledge:import
```

该命令会先构建服务端，再执行导入程序。成功时会输出导入的文档数量和数据库路径，例如：

```text
Imported 3 knowledge documents to /path/to/data/knowledge.db
```

建议按以下顺序维护：

1. 编辑或新增 `knowledge/*.md`；
2. 检查每个文件的 `id` 是否唯一、frontmatter 是否闭合；
3. 执行 `pnpm knowledge:import`；
4. 查看输出的文档数量是否符合预期；
5. 重启后端或重新打开分析任务，让新知识库被新的任务读取；
6. 运行测试：

```bash
pnpm typecheck
pnpm test
```

如果只修改了 Markdown 材料，通常不需要重新构建扩展；但必须重新导入知识库。正在运行的后端通过只读方式打开 `data/knowledge.db`，实际使用的版本以任务创建时能读取到的数据库为准。为避免版本混淆，建议导入后重启服务再进行验证。

## 6. 版本管理建议

应提交：

- `knowledge/*.md` 源材料；
- 必要的测试样例；
- 本文档。

通常不应提交：

- `data/knowledge.db`；
- `data/app.db`；
- `data/snapshots/` 下的网页快照；
- 日志、临时浏览器配置和测试运行产物。

项目的 `.gitignore` 已忽略数据库、快照和日志相关生成物。多人协作时，先合并源 Markdown，再由执行环境重新运行 `pnpm knowledge:import`，不要手工编辑 SQLite 文件。

## 7. 常见问题

### 导入数量为 0

确认文件直接位于 `knowledge/`，扩展名是 `.md`。当前导入脚本不会递归读取子目录。

### 导入时报重复 ID

检查多个文件的 `id` 是否相同。ID 是数据库主键，必须唯一。

### 修改后模型仍像在使用旧内容

确认已经重新执行 `pnpm knowledge:import`，并检查输出的文档数量。然后重启后端、重新创建分析任务；旧任务不会自动重写已经生成的分析结果。

### `source_url` 没有自动更新

这是预期行为。当前知识库导入是离线流程，`source_url` 只作为来源记录。需要更新材料时，应人工核对来源、修改 Markdown，再重新导入。

### 为什么模型没有引用某份材料

模型先根据查询词检索全文索引，结果受材料措辞、分节方式和查询范围影响。可以改进标题和正文中的关键术语，但不要为了“命中”而堆砌关键词。对于必须稳定使用的规则，应在分析提示词或测试中明确覆盖场景。
